## 软件 Task 1 实际记录

最初状态为干净群组。提交 Task 1 后，记录如下：

- Run：`r1`
- 根任务：`t1`
- Run 状态：`running`
- 根任务状态：`running`
- `model_calls`：6
- 已返回 token：0
- `fatal_error`：`false`
- 根任务错误计数：2
- 队列：`t1`
- 待回答人工请求：0

实际错误事件：

1. 提供方主动关闭连接。
2. 完整请求达到超时上限。
3. 再次主动关闭连接。
4. 缩短输出上限后仍达到超时上限。
5. 完整系统提示下只要求一个简单 plan 动作也达到超时上限。
6. 延长总时限后，提供方在有限重试后仍关闭连接。

最小连通探测很快成功，但完整编排系统提示下的动作生成没有成功返回。因此当前阻塞点位于 HKGAI 模型/网关的较长 JSON 动作请求，而不是本地消息总线、任务状态机或 Docker。

任务没有被标记为失败或完成，也没有触发自动人工澄清。保留 `running + queue=[t1]` 是现有恢复设计：提供方恢复后可以继续同一运行，不必新建重复根任务。

## 本次发现的修复

真实运行暴露出两个传输层问题，已增加回归测试：

- 提供方主动断开连接此前会作为普通动作错误进入 Engine；现在会作为可恢复传输错误执行有限客户端重试。
- `LLM_REQUEST_TIMEOUT_SECONDS` 文档允许配置，但 socket 曾硬性封顶为 120 秒；现在会使用配置值。

这两项修复改善重试和超时行为，但不等于 Task 1 已经通过。
