## 为什么不能完成

1. **会使用工具，不等于会推进交付。** 软件看板原尝试 80 个动作未写出交付；新闻第一题 108、基金第一题 130 个动作后仍反复读取。原控制器按重复结果停止，但没有在停止前要求阶段成果。已有阅读台账和“建议写草稿”的提示不足以约束模型。
2. **来源受阻被当作程序故障。** 403、连接重置、正文过大与参数错误一起累计 errors；三次后产生“Resolve the problem”人工请求。人类无法用回答解除网站 403；相同 URL 还会被别的角色或 PDF 工具再次请求。
3. **跨题继承过量。** 旧产物登记、重复计划、旧来源/论断占据上下文。模型反复读取已读内容，实际工具错误有时被最新工具页面挤走。早期又出现维护日志被当作永久客户需求的问题。
4. **局部检查没有覆盖完整协作链。** 第二轮软件冷启动的 API、浏览器局部检查通过，但 360 动作内没有完成最终审查。工程回归有替身响应，不能证明规划、交付、独立审查、人工验收整条链一定成功。
5. **数据交接与任务契约曾不充分。** 第二题必须绑定已验收 b4、显式导入源码、登记实际预约快照；仅说“继续之前的系统”不能保证角色拿到同版本输入。操作员曾填入说明字符串而非结构化 inputs，已保留更正事件。
6. **部分验收门槛来自模型自行规划。** 研究角色设置多来源、精确引文及独立审查后，需要真实原文和剩余预算；实际访问不足时不能靠搜索摘要、主观自评分或改成“已完成”绕过。

因此，目前六题不是全部通过：预约系统已验收；看板、两项新闻、两项基金任务尚无完整通过证据。部分论断、草稿、代码文件不等于最终交付。

## 本次已实现的流程修复

### 1. 从提醒变为有状态的阶段检查点

`collab/recovery.py` 从当前 task 的实际工具结果计算连续未写出成果的调用次数。工作任务计划完成后，达到 12 次进入 output_checkpoint。提供给模型的工具描述与网关共同限制到文件写入、产物发布和工作集记录；读取与执行工具暂时不开放。模型可先写小步代码或有证据归属、明确缺口的草稿，也可提出必要澄清。

成功写出文件、论断或产物后，下一次组装上下文恢复原本允许的工具。失败写入不清零；memory.working_set 不清零。不会扩大原工具权限。正式 review 类型任务豁免，以免独立审查被迫修改被审材料。

这是中间成果检查点，不是自动验收：草稿允许有未解决项，但最终 finish/review 仍必须满足原条件、独立证据和版本检查。该机制也不能证明每次写文件都是有效进展，后续仍需内容审查。

### 2. 来源失败分类、去重与有限重试

`Tools.execute_for_task` 对公开正文/PDF 下载增加失败策略：

- 403、404、410 和正文大小超限：同一 run 的公共 URL 最多实际请求一次。
- 连接、超时、429、可恢复服务端错误：最多两次实际尝试；不是无限重试，也不会恢复动作预算。
- 原生 curl 与 urllib 的已知访问错误使用相同策略。
- 公共失败按 run 范围复用，私信按 task 范围隔离；同一 URL 换成 PDF 工具不会绕过去重。
- 结果明确 ok=false / source_unavailable，保留原因和“未读取、未核实”的提示。模型可选其他可访问原文或在草稿中记录缺口。
- 权限、私网、格式契约及未知异常仍抛出，不把安全拒绝包装成成功。TLS 验证、地址检查、大小限制未关闭。

这避免了普通来源错误直接触发泛化的三次程序错误人工请求；它不保证被封锁的网站可以访问，也不自动选择或证明替代来源。

### 3. 已保留的前轮修复

当前 run 的来源/论断优先、历史显式调取；目标与验收只传一份；原始约束保留；阅读/检验台账；最新错误与不同观察并存；同任务相同 PDF 正文复用来源身份。完整记忆与恢复规则见 [记忆管理](memory-management.md)。
